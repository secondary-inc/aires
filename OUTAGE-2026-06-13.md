# Aires prod ingest outage — diagnosis + fix (2026-06-13)

## Symptom

Aires was "not receiving shit from anything" in prod. ClickHouse `aires.events`
held **5 rows total**, newest dated **2026-04-24** (~50 days stale). The two
`collector` pods were healthy (30d uptime, 0 restarts) but their logs contained
**zero** `[Server] Received batch` lines — i.e. no client ever successfully
delivered a batch. The only log lines were a ClickHouse keepalive disconnecting
every ~5.5h while idle.

~18 prod services across many namespaces are configured with
`AIRES_ENDPOINT=http://collector.aires.svc.cluster.local:4317` (plaintext) and
none of them were shipping anything.

## Root cause(s)

Two independent bugs, both on the **client/SDK side**, both producing the same
silent "no events" outcome:

1. **TLS default vs plaintext collector.** The Rust SDK config builder defaulted
   `tls = true` (`packages/sdk-rust/src/config.rs`). The collector serves
   plaintext h2c on :4317 (no certs; `GRPC.Server.Supervisor` + Bandit
   `scheme: :http`). A client pointed at `http://collector:4317` therefore
   attempted a TLS handshake against an h2c port, `GrpcClient::connect` failed,
   and `BatchWorker::run` logged to `tracing` (no subscriber installed = silent)
   and **returned permanently**. Every later event filled the bounded queue and
   was dropped. Net: zero events shipped.

2. **`@aires/sdk@0.2.0` ships no prebuilt native binary.** Prod pods run SDK
   `0.2.0`, whose `node_modules/@aires/sdk/native/` contains only Rust source —
   no `.node`. The TS layer's `require()` of the addon throws, so it falls into
   the stdout-only fallback (`packages/sdk-ts/src/index.ts`) and never ships at
   all. (The prebuilt-binary feature landed after 0.2.0, in commit `bccce12`.)

A third, non-outage data-quality bug surfaced while verifying the fix:

3. **Collector lost severity + event timestamp.** protobuf-elixir decodes enum
   fields to atoms (`:INFO`), but `Transform.severity_to_string/1` only matched
   integers, so every row's severity became `unspecified`. And `Store` never
   inserted the `timestamp` column, so ClickHouse stamped rows with ingest time
   via the `now64()` DEFAULT (identical timestamps within a batch, lost
   ordering).

## Fixes (committed on `main`)

- `0f3b9be` `fix(sdk)` — derive TLS from the endpoint scheme (`https://` ⇒ TLS,
  else plaintext) unless explicitly set; make the batch worker connect lazily
  and reconnect on demand so a transient/late collector never permanently
  disables telemetry. +5 unit tests.
- `8703cb6` `fix(collector)` — match protobuf severity atoms (integer/string
  fallbacks kept); insert the SDK-supplied timestamp as a `DateTime64(9)`
  literal, falling back to `now64()` only when absent. +1 test.
- `aa15017` `chore(sdk)` — bump `@aires/sdk` to `0.5.0`.

### Verified end-to-end locally

Against the local stack (plaintext collector on :4317 + ClickHouse, identical
config to prod) the fixed SDK shipped events that the collector received and
inserted, with **correct severities** (`info`/`warn`/`error`, not
`unspecified`) and **distinct nanosecond event timestamps**:

```
[Server] Received batch: 3 events from aires-sdk-rust/0.1.0
[Store] Inserted 3 events
```

- Rust SDK unit tests: 26 pass. Collector tests: 9 pass.
- A fixed **linux-x64** native addon is staged via `scripts/build-linux.sh`.

## Notes / follow-ups

- The SDK worker now logs connect failures at `warn` and retries; consider
  installing a `tracing` subscriber in hosts so these are visible.
- `Store.do_insert` still omits `id` (uses CH `generateUUIDv4()` default). Fine
  for now; wire it through if event-ID dedup is needed.
- Consider a startup self-test event from each service so a future ingest stall
  is caught by an alert rather than by eyeballing row counts.
